How Docker actually runs containers under the hood:

Layer 1 — Docker CLI
You type commands like docker run or docker build.
The CLI sends those commands to the Docker daemon (dockerd) via a REST API.

Layer 2 — dockerd
This is the Docker daemon, the brain of Docker.
It handles Docker‑specific tasks such as:

Managing images, networks, and volumes

Authenticating with Docker Hub

Exposing the REST API

It’s the part that makes Docker “Docker.”



Layer 3 — containerd
This is a general container runtime, not Docker‑specific.
It’s responsible for:

Pulling images

Managing container lifecycles (start, stop, supervise)

Handling container metadata

Kubernetes talks directly to containerd, skipping dockerd entirely — that’s why the diagram shows the Kubernetes logo pointing to it.



Layer 4 — runc
This is the low‑level launcher that actually starts containers.
It implements the OCI (Open Container Initiative) standard, meaning it’s compatible with other runtimes too.
It interacts directly with the Linux kernel using:

namespaces (for isolation)

cgroups (for resource limits)

exec (to run processes)


Bottom layer — Linux kernel
The foundation that provides the isolation and resource control mechanisms containers rely on.




cgroups reminder:

Great memory check, Dani — cgroups (short for control groups) are a Linux kernel feature that Docker and other container runtimes use to limit and isolate system resources for each container.

Here’s how they fit in:

⚙️ What cgroups do
Resource limits — cap how much CPU, memory, disk I/O, or network bandwidth a container can use.

Isolation — prevent one container from hogging resources and starving others.

Accounting — track resource usage per container for monitoring and billing.

Prioritization — assign CPU shares or weights so critical containers get more compute time.

When you run:

bash: docker run --memory=512m --cpus=1 nginx
Docker translates those flags into cgroup rules that the kernel enforces — ensuring the container never exceeds 512 MB RAM or one CPU core.


Relationship to other layers
In the diagram you shared:

runc applies cgroup settings when launching containers.

The Linux kernel enforces them.

Higher layers (containerd, dockerd) just pass configuration down.

/////////////////////////////Volumes //////////

Docker keeps volumes under /var/lib/docker/volumes/ on the host.

Each volume (like datavolume) is a directory that Docker manages.

When you run a container with a volume mount, Docker connects that host directory to a path inside the container.

Host path:
/var/lib/docker/volumes/datavolume   - where datavolume a name which we give
In the running docker path will be:
/var/lib/sql

Example:
docker volume create datavolume
docker run -v datavolume:/var/lib/mysql mysql

Second option is BIND MOUNT :

Bind mounts are another way to connect storage between your host and containers, but they behave differently from Docker volumes.

A bind mount directly links a specific directory or file on your host to a path inside the container.
Example:docker run -v /home/dani/app:/usr/src/app node


This means:

/home/dani/app on your host is mounted inside the container at /usr/src/app.

Any changes you make in either place instantly appear in the other.

When to use bind mounts
Use them when you need real‑time access to local files:

Development environments — edit code on your host and see changes live inside the container.

Configuration sharing — mount config files or secrets from your host.

Debugging — inspect logs or temporary data directly from your host.



Feature	                 Bind Mount	                     Named Volume
Location	Any host path you specify	        Managed under /var/lib/docker/volumes/
Lifecycle	Exists as long as the host path exists	Managed by Docker (can be created/deleted via CLI)
Portability	Tied to your host filesystem	        Portable between hosts via Docker
Use case	Development, debugging	                Persistent data (databases, production apps)

Modern way to BIND MOUNT:

docker run --mount type=bind,source=/data/mysql,target=/var/lib/mysql mysql

Notice that we didn't have to write the data again - it was already saved to the host directory /opt/data during the previous container run.

When we ran the container this time, the data was picked up from the same path automatically.

This is how Docker volumes give us data persistence!


Because named volumes are global objects, not tied to any container.

You can list them:docker volume ls

You can inspect them:docker inspect mysql_data

You can delete volume manually: docker volume rm mysql_data

But Docker will never delete a volume automatically unless you explicitly ask it to (e.g., docker rm -v or docker volume prune).
